# 网页端聊天工具适配 · 设计文档

- 日期：2026-09-23
- 状态：已与需求方逐块确认，待评审
- 范围：把 chat-jev 从「只读微信桌面版」扩展成「读浏览器里的聊天网页」，微信桌面版保留

## 1. 目标与非目标

**目标**：用户在浏览器里打开 WhatsApp Web、Telegram Web、Slack、Discord、Teams 等聊天网页，
侧边栏实时给出对方这句话的意图、风险等级、行动建议和候选回复，点一下把候选填进输入框。

**首批验证站点**：WhatsApp Web、Telegram Web、Slack、Discord、Teams。

**非目标**：

- 不做页内浮层，只用 Chrome Side Panel。
- 不做网页版的 YOLO 检测框——那是画在微信窗口上的东西，侧边栏没有对应物。
- 不在浏览器里跑本地大模型（decider-2b 有 7 GB，WebGPU 方案不现实）。
- 不自动发送任何消息，不调用任何聊天平台的官方接口。

## 2. 已定决策

| 决策点 | 结论 |
|---|---|
| 读页面的方式 | Chrome 扩展读 DOM |
| 主界面 | Chrome Side Panel；macOS 原生悬浮窗保留为可选 |
| 微信桌面版 | 保留，改造成另一个数据源 |
| 候选与界面语言 | 候选回复英文，侧边栏界面英文；中文那套留给微信端 |
| 触发方式 | 全部自动，加刷屏保险丝 |
| 判断层部署 | 默认云端，本地 Python 服务可选 |

## 3. 总体结构

```
┌─ Chrome 扩展 ────────────────────────────┐
│  站点适配器  →  调度器  →  侧边栏 UI      │
│  (读 DOM)      (决定何时  (意图/风险/候选) │
│                 判断生成)                 │
└───────────────────┬──────────────────────┘
                    │  分析接口（同一形状）
        ┌───────────┴───────────┐
        ↓                       ↓
   云端直连                 本地 Python 服务
   (Jev / OpenAI 兼容)      (decider-2b + 本地排序)
                                ↑
                        微信桌面版 OCR + 原生悬浮窗
```

两个契约把系统切成互不知情的几块：数据源只管产出会话快照，界面只管消费分析结果，
判断后端在云端还是本机对上下游都不可见。

扩展直连模型服务商意味着 API key 存在扩展存储里（网页读不到），
并且扩展要申请访问这些 API 域名的权限。这是「不装本地服务也能用」的必然代价。

## 4. 契约一：会话快照

站点适配器唯一的职责是产出这个结构。它替代现在的 `read_conversation()`。

```json
{
  "source": "whatsapp",
  "conversationId": "…",
  "title": "…",
  "isGroup": false,
  "messages": [
    {"id": "…", "text": "…", "sender": "…", "isSelf": false,
     "ts": 1758585600, "mentionsMe": false}
  ],
  "input": {"canFill": true}
}
```

- `id`：站点给了就用站点的；没有就用「内容 + 位置」哈希，用于去重。
- `isSelf`：三值——`true` / `false` / `null`。`null` 表示方向未确认。
- `mentionsMe`：频道场景用，当前不参与触发判定（触发是全自动），只做面板标记。

微信桌面版走同一结构：`perception.py` 的 `Message` 已经有 `text`、`side`、`sender`，
缺的 `id` 和 `ts` 用内容加位置哈希补上，`side` 的 `"unknown"` 映射成 `isSelf: null`。

## 5. 契约二：分析接口

三个动作，云端和本地形状一致，调度器不关心谁在后面答。

| 动作 | 入参 | 出参 |
|---|---|---|
| `judge` | `{text, context, lang}` | `{intent, confidence, intent_probs, risk, risk_probs, actions}` |
| `generate` | `{text, context, intent, tones, lang, platform}` | `{groups: [{tone, texts}], model, error}` |
| `rank` | `{text, intent, candidates}` | `[{text, prob}]` |

出参形状和现有 Python 实现一致（`judge.Judge.judge`、`Generator.generate`、
`rank_candidates`），这样本地服务只是把现有函数包一层 HTTP，不改内部。

`lang` 和 `platform` 是新增的：生成层的提示词要按语言和平台改口径，见第 8 节。

## 6. 站点适配层

每个站点一份声明式适配文件：

```
match:    哪些 URL 归这个适配器
root:     消息列表容器
message:  单条消息，以及 text / sender / ts / id 的取法
isSelf:   方向判定（见下）
input:    输入框，以及填入方式
```

结构特别怪的站点（例如 Teams 的某些视图在 iframe 里）允许写一小段 JS 接管。

**方向判定按可靠性排队**，前一条不成立才往下走：

1. 站点自己的标记（收发方向的 class 或 data 属性）
2. 发送者名等于当前登录用户名
3. 气泡的水平位置

三条都不成立标成 `isSelf: null`，**不作为回复目标**。这继承 `perception.message_side()`
的保守原则：宁可漏一条，不能把自己说的话当成对方在催你。

**不在本文档写死各站选择器**。那些 class 名经常变，写进设计就是假精确。
第 1 期用扩展在真实页面上探一遍，把选择器和信号连同探测日期记进适配文件。

**改版自检**：每个适配器带自检——找不到容器、或读到的消息数为零，
侧边栏直接显示「这个站点可能改版了」。现在微信那套改版后只显示「等待消息」，
用户不知道发生了什么，这个坑不带过来。

**未适配站点**走通用启发式：`role="log"`、`role="list"` 等无障碍标记，加重复兄弟节点结构；
输入框找 `contenteditable` 或 `textarea`。能认出就标「通用模式，方向可能不准」，
认不出就明说不支持。「所有站点」靠这条兜底，不宣称它准。

**变更监听**用 MutationObserver，不用定时轮询。但保留现有的停稳逻辑：
对方连发时等 1.2 秒停稳再分析（`hud.py` 的 `SETTLE_S`）。
Slack、Discord、Teams 都是虚拟滚动，只读可见的一屏，上下文本来也只要最近几条。

## 7. 调度与触发

**只分析当前标签页的当前会话**。后台标签页只记未读数，不判断不生成。这是成本和性能的总闸。

**触发条件**：活动会话里出现一条 `isSelf: false` 的新消息 → 停稳 1.2 秒 → 判断和生成同时起跑。
同一会话最小间隔沿用 `MIN_GAP_S = 2.0`。

**在途结果作废**：现有代码已有 epoch 守卫（结果回来时检查文本是否仍是最新、话术有没有换过）。
网页端加两个作废条件：切了会话、切了标签页。

**自己发了消息就收起候选**。微信端因为方向判断不可靠不敢做，网页端方向可靠，可以做。

**预判加预生成的并行照搬**（`_prejudge_loop` / `_pregen_loop` 的 latest-wins 槽位）。
网页端的差别只是判断可能走网络而不是本地模型，时序反而更简单。

**刷屏保险丝**：单个会话一分钟内超过 20 条新消息时，暂停自动分析，
面板顶部显示「这个频道太活跃，已暂停自动分析」加一个恢复按钮。
用户点恢复后，该会话在这个标签页存活期间不再自动熔断，避免反复弹。

## 8. 判断、生成、排序

**判断层三个后端**，优先级同现在（配了什么用什么）：云端 Jev、本地 decider-2b、
通用大模型兜底（给只有一个 OpenAI 兼容 key 的用户）。

**英文效果先测再写**。第 1 期造 30–40 条英文回归集（Slack 式工作对话与 WhatsApp 式私聊各一半），
三个后端各跑一遍。结论决定默认后端，也决定要不要改意图体系——
现有 8 类意图照中文职场训练，英文团队协作大体能对上，Discord 那类社交场景可能对不上。

**提示词是并列两套，不是替换**。判断层措辞对准确率极敏感：
项目实测两轮压缩分别掉到 81.8% 和 77.3%，原文 86.4%（见 `judge.py` 的 `INTENTS` 注释）。
英文提示词要按英文回归集重新调，中文那套一个字都不能动——微信桌面版还在用。

**共享定义**：意图、风险分级、行动建议、话术搬进 `shared/definitions.json`，中英两套文案，
Python 和 TypeScript 都从它读。这是防止两套实现跑偏的落点。

**生成层参数化**：`PROMPT_ONE` 里写死的「微信消息」「微信里打字的语气」「不超过 30 个字」
改成平台名、语言、长度上限。英文长度另立口径——30 个汉字和 30 个英文单词不是一回事。

**英文话术另起一套**。「贴吧老哥」「卑微乙方」翻成英文没有意义。
10 条人设每条都要写清「什么语气 + 别变成什么」，这是内容工作量。中文那套原样留给微信端。

**排序**：配了 Jev 的云端模式用 `evaluate` 的 choice 打分（`judge_jev.rank_candidates` 已实现）；
本地服务模式用 decider-2b；只有 OpenAI key 的用户没有排序，
面板**不显示概率数字**，而不是编一个出来。

## 9. 侧边栏与填入

**用 Chrome Side Panel**。跟着标签页走，不遮挡页面，不用算窗口坐标，不往页面塞 DOM。

**信息架构照搬现有面板**（已验证）：顶部会话名、分析状态、正在处理哪条消息；
中间意图、识别率、风险等级、行动建议；底部按话术分组的候选，每条右侧复制与填入。界面文字英文。

**填入**是网页端最容易翻车的地方。Slack、Discord、WhatsApp 用的都是富文本编辑器，
直接改 DOM 内容它们不认——编辑器维护自己的内部状态，改了 DOM 下一次渲染就覆盖回去，
或者发出去是空的。要派发真实输入事件，具体哪种手段管用每站单独验证，与选择器探测一起做。

三条原则从 `fill.py` 继承，一条不能松：

1. **不自动发送**，永远由用户按回车。
2. **不覆盖已有草稿**，有草稿就提示改用复制。
3. **写完读回确认**，失败明说原因，不自动重试。

不用系统剪贴板（`fill.py` 顶部注释写了为什么不走剪贴板加 Cmd+V）。

**权限按站点申请**。不要「访问所有网站」，用可选权限，用户在哪个站点点启用就授权哪个；
通用启发式模式同理，用户主动点「在这个站点试试」才注入。

**原生悬浮窗**改成从本地服务读结果流即可复用——它的渲染入口
（`applyJudgment_` / `applyCandidates_`）本来就是消费 payload 的形状。

## 10. 仓库结构与共享定义

现有 Python 原地不动，扩展并列进来：

```
extension/        TypeScript，Chrome MV3
  adapters/       站点适配文件 + 通用启发式
  scheduler/      触发、去重、作废守卫、刷屏保险丝
  backends/       judge / generate / rank 的云端实现
  panel/          侧边栏界面
  fill/           各站点输入框写入
shared/
  definitions.json   意图、风险、行动建议、话术，中英两套
  contracts.md       会话快照与分析接口的形状
src/              现有 Python
  service.py         新增：本地分析服务，形状同云端
  sources/wechat.py  新增：perception 输出转会话快照
```

## 11. 测试策略

- **适配器**：真实页面存成脱敏 HTML 快照，离线跑解析，断言消息条数、方向、发送者。
  站点改版时更新快照就是一次回归。不每次开真浏览器。
- **判断层**：新的英文回归集，加现有的中文 22 条（`judge_zh_test.py`）。中文那套是不能退的底线。
- **调度器**：写成纯函数，用合成事件序列测去重、停稳、作废、保险丝。
- **填入**：只能真人手测，每站一份检查清单。没有别的办法。
- **Python 侧**：现有 `tests/` 全部保留并继续通过。

## 12. 分期计划

1. **探测**：英文判断回归集跑三个后端；五个站点探 DOM 结构、方向信号、填入手段。
   产出探测报告，不写产品代码。
2. **骨架**：`shared/definitions.json`、两个契约、扩展骨架；一个站点跑通
   「读 DOM → 云端判断 → 侧边栏出结果」。
3. **第一个站点做透**：站点由第 1 期的探测结论选定（DOM 结构最清楚、填入手段最稳的那个），
   含填入、保险丝、改版提示。
4. **铺开其余四站**。
5. **通用启发式兜底**与未适配站点提示。
6. **本地服务**：judge / generate / rank 包成 HTTP；微信端改接快照接口；原生悬浮窗接本地服务。
7. **英文话术与文案**；README 与 PRIVACY 改口径。

第 1 期的结论可能推翻后面的安排（例如三个后端的英文效果都不行，第 8 节的默认后端要重选），
这是有意这么排的。

因此实施计划**先只覆盖第 1–2 期**：探测报告出来之后，再按结论为后续各期分别出计划。
一次把七期全部写成计划，等于把还没探到的东西当成已知。

## 13. 风险与开放问题

**「零封号风险」这句话在网页端要改口径**。只读 DOM、不调官方接口、不自动发送，
被检测到的可能性很低，但 Discord 的服务条款明确禁止修改客户端行为，WhatsApp 也有类似条款。
微信桌面版那套「看屏幕不碰程序」的说法不能照搬。README 与 PRIVACY 相应段落要重写，
措辞在第 7 期定稿前逐条对照各站条款。

**英文判断效果未知**。86.4% 是 22 条中文的口径。第 1 期出结论前，不承诺任何英文准确率。

**Teams 待探测**。网页版使用率和 iframe 情况探过才知道，可能降到最后做。

**Chrome 商店审核**。读取聊天内容的扩展审核严格，需要隐私政策页面。
如果只自用或发 crx 手动安装，这条不适用——上架与否由需求方在第 2 期前决定。

**两套实现的漂移**。TypeScript 与 Python 各有一份判断生成调度逻辑，
靠 `shared/definitions.json` 和对拍测试约束。定义文件之外的逻辑漂移只能靠评审发现。
